# Staging release runbook

Isolated pre-production target: **staging Worker + staging Supabase project + staging Pages
project**, PayPal **sandbox**, Clerk **development instance**, no paid AI provider keys.

Production deployment, live PayPal processing and paid AI remain unauthorised. Nothing in steps
4–7 should be run without that decision being made explicitly.

## 1. Staging database (separate project — never `--linked`, never the production connection string)

```bash
supabase projects create prism-file-hero-staging        # or the dashboard; note the project ref
cd supabase && supabase link --project-ref <staging-ref>   # local link only; do not use --linked elsewhere
supabase db push --db-url "postgresql://postgres:<staging-password>@db.<staging-ref>.supabase.co:5432/postgres"
```

Verify, read-only, that the ledger objects exist:

```bash
psql "postgresql://postgres:<staging-password>@db.<staging-ref>.supabase.co:5432/postgres" -c \
  "select p.proname from pg_proc p join pg_namespace n on n.oid=p.pronamespace
     where n.nspname='public' and p.proname in ('check_usage_limit','reserve_usage','settle_usage','refresh_user_coverage','get_user_entitlement') order by 1"
```

Expected: all five. `check_usage_limit` must report `free` AI pages `0` and a Pro caller `-1`.

## 2. Staging KV namespace

```bash
npx wrangler kv namespace create STAGING_KV --text   # then set [[env.staging.kv_namespaces]].id
```

Staging must not share the production namespace: device records and reservations would cross
environments.

## 3. Secrets for the staging environment only

```bash
cd worker
npx wrangler secret put SUPABASE_URL                 --env staging   # https://<staging-ref>.supabase.co
npx wrangler secret put SUPABASE_SERVICE_ROLE_KEY    --env staging   # staging key, never the production one
npx wrangler secret put PAYPAL_CLIENT_ID             --env staging   # sandbox app
npx wrangler secret put PAYPAL_SECRET                --env staging   # sandbox secret
npx wrangler secret put PAYPAL_WEBHOOK_ID            --env staging   # created in step 5
npx wrangler secret put PAYPAL_PLAN_PRO_MONTHLY      --env staging
npx wrangler secret put PAYPAL_PLAN_PRO_ANNUAL       --env staging
npx wrangler secret put PAYPAL_PLAN_BUSINESS_MONTHLY --env staging
npx wrangler secret put PAYPAL_PLAN_BUSINESS_ANNUAL  --env staging
```

Deliberately **not** set: `NVIDIA_API_KEY`, `GROQ_API_KEY_*`, `MISTRAL_API_KEY_*`. With no provider
configured, `/api/ai` answers 502 and settles its reservation to ERROR — staging cannot spend money
on AI, which is the point.

## 4. Build the artifact from the committed tree

```bash
git stash list && git status --porcelain          # must be clean; deploy only what is committed
npm ci && npm run release:build && npm run check:release
```

`deploy/` = marketing site at `/` + the React app at `/app/` + `deploy/_worker.js` router. Asset
URLs are `/app/`-relative and the fingerprinted site assets come from the generator.

## 5. Deploy the staging Worker, then wire the PayPal sandbox webhook

```bash
cd worker && npx wrangler deploy --env staging
npx wrangler tail --env staging &            # keep logs while the webhook is exercised
curl -s https://prism-worker-staging.<account>.workers.dev/api/health
```

Create the sandbox webhook in the PayPal developer console against
`https://prism-worker-staging.<account>.workers.dev/api/paypal/webhook` for
`BILLING.SUBSCRIPTION.CREATED`, `...ACTIVATED`, `...CANCELLED`, `PAYMENT.SALE.COMPLETED`,
`PAYMENT.SALE.REFUNDED`, `CUSTOMER.DISPUTE.CREATED`; put its id in `PAYPAL_WEBHOOK_ID`.

Then confirm a real delivery is verified and stored, and that a tampered one is refused
(`npm run check:paypal-capability`, `check:paypal-sandbox`).

## 6. Deploy the staging Pages project (separate project name — never `prism-file-hero`)

```bash
npx wrangler pages project create prism-file-hero-staging --production-branch main
npx wrangler pages deploy deploy --project-name=prism-file-hero-staging --branch=main
```

Point the staging app at the staging Worker and the Clerk **development** publishable key:

```bash
# .env.staging (gitignored): VITE_WORKER_URL=https://prism-worker-staging.<account>.workers.dev
# VITE_CLERK_PUBLISHABLE_KEY=<dev instance pk_test_…>
```

`ALLOWED_ORIGINS` / `FRONTEND_URL` in `[env.staging.vars]` must match the Pages origin exactly, or
checkout returns to a page the browser cannot call.

## 7. Verification at staging (the gate before any production decision)

```bash
APP_URL=https://prism-file-hero-staging.pages.dev WORKER_URL=https://prism-worker-staging.<account>.workers.dev \
  node scripts/clerk-journey-check.mjs --phase=auth
# … --phase=upgrade (sandbox buyer approval), then --phase=verify
APP_URL=… WORKER_URL=… node scripts/paid-tool-output-check.mjs --live
APP_URL=… WORKER_URL=… node scripts/checkout-return-check.mjs
node scripts/auth-isolation-check.mjs            # staging config must carry no synthetic-auth marker
node scripts/prod-auth-check.mjs                 # read-only, production, unchanged
```

Pass criteria are the same numbers as the local table above. Any regression here blocks production,
it does not authorise a workaround.

## 8. Rollback and recovery

```bash
cd worker && npx wrangler deployments list --env staging && npx wrangler rollback --env staging
npx wrangler pages deployment list --project-name=prism-file-hero-staging   # promote a prior build
pg_restore -d <staging-db> --no-owner backup.sql                            # after re-creating roles
```

During a database recovery window: PayPal keeps delivering webhooks (they are retried), the
Worker's `GET /api/billing/entitlement` fails closed so no new paid access is granted, existing
browser sessions keep their cached UI but every server check answers honestly, and events received
while the ledger is unavailable are replayed from PayPal's resend API rather than reconstructed —
`billing_events.payload` stores exactly what PayPal delivered. Rollback to an older Worker with a
newer schema is safe for reads; rollback to an older **schema** can strand coverage because the
paid projection is derived from payment rows, and that derivation is what changed. Full detail in
`docs/audit/baseline.md` §35.

## Explicitly out of scope

`wrangler deploy` for the default environment, `pages deploy --project-name=prism-file-hero`,
production PayPal credentials, and any paid AI provider key.

Verified, with results:

- `scripts/staging-probe.mjs` — **26/26**: every data route 401s anonymously; malformed and
  shape-correct forged tokens are refused; a genuine Clerk **development** session token
  (`iss …clerk.accounts.dev`) passes staging authentication; `subscribe` answers
  `503 configured:false` rather than granting; cloud AI never returns 200 with no provider
  credentials and claims no completion; CORS accepts the staging Pages origin, does not vouch for
  `prismfilehero.com`, and does not echo an arbitrary origin; `/`, `/app/`, a deep link, a missing
  asset (real 404), `robots.txt` and `X-Robots-Tag: noindex` all behave.
- Staging artifact check (`PRISM_ARTIFACT_ENV=staging npm run check:release`) — **26/26**; the
  production path still passes its own 20 unchanged.
- Staging database: fresh install applied all 19 migrations; `check:backend` against it **32/32**
  (RLS boundaries, privilege grants, billing ownership, ledger reserve→settle, dedupe surviving a
  PostgREST restart); `pg_dump` (372,911 bytes, `evidence/staging/staging-backup.sql`) restored
  into a separate database in the same image with 10 tables, 4 RLS policies and all 6 ledger
  functions, and the restored copy answers the quota policy identically.
- Deployed UI screenshots in both themes and both viewports: `evidence/staging/staging-{home,app}-{desktop,mobile}-{light,dark}.png`.

Two defects the staging work exposed, both fixed:

1. **The first staging Pages deployment carried production bindings.** The release build reads
   `.env.production`, so the deployed bundle called the live Worker and embedded the `pk_live`
   Clerk key, and `site/assets/features.data.js` carried both as well. A `--mode staging` build
   path (`.env.staging`, gitignored), a mode-aware Worker fallback in `services/apiConfig.ts`, a
   staging rewrite of the marketing bundle's Worker/Clerk values in `build-release.mjs`, and a
   guard in `release-artifact-check.mjs` that fails on the exact production values now prevent it.
   `vite.config.ts` keys `base` off the build command, so a staging build still mounts at `/app`.
2. **`release-artifact-check` silently depended on a `pages dev` already running on 8790**, which
   meant a leftover server could have supplied a different artifact than the one under test. It now
   starts and stops its own runtime.

Not exposed publicly, on purpose: the staging Supabase stack authenticates with Supabase's
well-known local JWT secret. Tunneling it would let anyone who knows that default mint a valid
`service_role` token for the tunneled PostgREST, so the deployed staging Worker is deliberately
left without `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` — every data route fails closed, which the
probe asserts rather than assumes.

Blocked, in order:

1. **Hosted staging database** — needs `supabase login` (interactive) or `SUPABASE_ACCESS_TOKEN`.
   Then: create the project, `supabase db push`, create the staging secrets
   (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`), and re-run the probe + journey against it.
2. **PayPal sandbox secret rotation** — no API exists for rotating REST app credentials; it is a
   dashboard action. Until it is rotated, the disclosed secret is not reused, so no sandbox
   subscription and no staging webhook can be created.
3. **Sandbox buyer approval** for the subscription, once (2) is done.
